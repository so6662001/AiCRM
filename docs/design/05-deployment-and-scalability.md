# AiCRM 部署与高并发架构设计文档

## 1. 百万并发架构设计

### 1.1 并发量拆解

```
目标：100 万并发用户

假设：
- 峰值 QPS ≈ 并发用户 × 平均每秒请求数
- 平均每用户每秒 0.5 ~ 1 次请求
- 峰值 QPS ≈ 50 万 ~ 100 万
- 读写比 ≈ 8:2（CRM 系统以查询为主）
- 读 QPS ≈ 40 万 ~ 80 万
- 写 QPS ≈ 10 万 ~ 20 万
```

## 2. 高性能优化策略

### 2.1 多级缓存架构

```
请求 → 本地缓存 (Caffeine) → Redis → 数据库

┌──────────────────────────────────────────────────────────┐
│                    多级缓存策略                            │
│                                                            │
│  L1: 本地缓存 (Caffeine)                                  │
│  ├── 租户基础信息         TTL: 10min   最大: 10,000 条     │
│  ├── 组织架构树           TTL: 5min    最大: 5,000 条      │
│  ├── 角色权限信息         TTL: 5min    最大: 10,000 条     │
│  ├── 商机阶段配置         TTL: 10min   最大: 1,000 条      │
│  ├── 违规词库             TTL: 5min    最大: 50,000 条     │
│  └── 公海池配置           TTL: 10min   最大: 1,000 条      │
│                                                            │
│  L2: Redis 缓存                                           │
│  ├── 用户 Session/Token   TTL: 2h                         │
│  ├── 客户详情缓存         TTL: 30min                      │
│  ├── 线索详情缓存         TTL: 30min                      │
│  ├── 用户数据权限缓存     TTL: 10min                      │
│  ├── 今日任务列表缓存     TTL: 5min                       │
│  ├── 仪表盘统计缓存       TTL: 5min                       │
│  ├── 分布式锁             TTL: 30s                        │
│  └── 限流计数器           TTL: 1s/1min                    │
│                                                            │
│  缓存更新策略：                                            │
│  ├── 写操作：先更新DB，再删除缓存（延迟双删）              │
│  ├── 读操作：缓存未命中时从DB加载并设置缓存                │
│  └── 一致性：通过 RocketMQ 广播删除各实例本地缓存          │
└──────────────────────────────────────────────────────────┘
```

### 2.2 读写分离

```
┌──────────────────────────────────────────────────┐
│               读写分离策略                          │
│                                                    │
│  写操作 → Master 库                                │
│  读操作 → Slave 库（多个从库轮询/权重）             │
│                                                    │
│  实现方式：ShardingSphere 读写分离配置              │
│                                                    │
│  强一致性读：                                      │
│  ├── 写操作后的立即读取 → 走 Master                 │
│  ├── 使用 HintManager 强制 Master 查询              │
│  └── 场景：创建后立即查看详情                       │
│                                                    │
│  最终一致性读：                                     │
│  ├── 列表查询 → Slave（允许短暂延迟）               │
│  └── 报表统计 → Slave                              │
└──────────────────────────────────────────────────┘
```

### 2.3 异步化处理

```
┌──────────────────────────────────────────────────┐
│               异步化策略                           │
│                                                    │
│  使用 RocketMQ 异步化的场景：                      │
│                                                    │
│  1. 录音文件上传完成 → 触发 AI 转写分析            │
│  2. 跟进记录创建 → 更新客户最后跟进时间            │
│  3. 线索分配 → 发送通知消息                        │
│  4. 客户审核通过 → 触发 ERP 同步                   │
│  5. 打卡签到 → 更新拜访记录状态                    │
│  6. 操作日志 → 异步写入审计表                      │
│  7. 数据变更 → ES 索引更新                         │
│  8. 统计数据 → 异步聚合计算                        │
│                                                    │
│  消息可靠性保证：                                   │
│  ├── 生产者：同步发送 + 事务消息                    │
│  ├── 消费者：幂等消费（唯一ID去重）                 │
│  └── 失败重试：最多 16 次 + 死信队列               │
└──────────────────────────────────────────────────┘
```

### 2.4 数据库优化

```
┌──────────────────────────────────────────────────┐
│               数据库优化策略                        │
│                                                    │
│  1. 分库分表 (ShardingSphere)                     │
│     ├── 分片键：tenant_id                         │
│     ├── 分库：tenant_id % 8（或16）               │
│     ├── 分表：tenant_id % 32                      │
│     └── 大租户：支持独立数据库                      │
│                                                    │
│  2. 索引优化                                       │
│     ├── 所有查询必走 tenant_id 前缀               │
│     ├── 联合索引遵循最左前缀原则                    │
│     ├── 覆盖索引减少回表                           │
│     └── 避免索引失效（函数、类型转换等）            │
│                                                    │
│  3. SQL 优化                                       │
│     ├── 禁止 SELECT *                             │
│     ├── 大表查询必须分页                           │
│     ├── 关联查询不超过 3 张表                      │
│     ├── 批量操作使用 Batch Insert                  │
│     └── 统计查询走 ES 或预聚合表                   │
│                                                    │
│  4. 连接池                                         │
│     ├── 使用 HikariCP                             │
│     ├── 最大连接数：50/实例                        │
│     └── 连接超时：3s                              │
│                                                    │
│  5. 数据归档                                       │
│     ├── 审计日志：6 个月后归档到冷存储              │
│     ├── 同步日志：3 个月后归档                     │
│     └── 录音文件：1 年后归档到低频存储              │
└──────────────────────────────────────────────────┘
```

## 4. 部署架构

### 4.1 Kubernetes 部署

```
┌──────────────────────────────────────────────────────────┐
│                    K8s 集群架构                            │
│                                                            │
│  集群规模：                                                │

│  ├── 节点规格：16C32G 或 32C64G                           │

│  命名空间划分：                                            │

│  ├── aicrm-biz        ── 核心业务服务                      │
│  ├── aicrm-support    ── 支撑服务（AI、文件、通知）        │

│  Deployment 配置要点：                                     │

│  └── 优雅关闭：preStop Hook + 30s 宽限期                   │
└──────────────────────────────────────────────────────────┘
```

### 4.2 HPA 自动伸缩配置示例

```yaml
# 以 aicrm-customer 服务为例
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: aicrm-customer-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: aicrm-customer
  minReplicas: 10
  maxReplicas: 80
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 70
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 30
      policies:
        - type: Percent
          value: 50
          periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
        - type: Percent
          value: 10
          periodSeconds: 60
```

### 5.2 告警规则

| 告警项 | 条件 | 级别 | 通知方式 |
|---|---|---|---|
| 服务不可用 | Pod 重启次数 > 3/5min | P0 紧急 | 电话 + 钉钉 |
| API 错误率 | 错误率 > 5%/1min | P1 严重 | 钉钉 + 邮件 |
| API 延迟 | P99 > 3s/5min | P1 严重 | 钉钉 + 邮件 |
| CPU 高负载 | CPU > 80%/5min | P2 警告 | 钉钉 |
| 内存不足 | 内存 > 85%/5min | P2 警告 | 钉钉 |
| MQ 积压 | 积压 > 10000/5min | P2 警告 | 钉钉 |
| 数据库慢 SQL | 慢查询 > 10/min | P3 提示 | 邮件 |
| 磁盘空间 | 磁盘 > 80% | P2 警告 | 钉钉 + 邮件 |

## 7. 容灾与高可用

```
┌──────────────────────────────────────────────────────────┐
│                    AI 服务架构                             │
│                                                            │
│  ┌──────────┐     ┌──────────────┐     ┌──────────────┐  │
│  │ 录音文件  │────▶│ ASR 语音转写  │────▶│ 文本分析引擎  │  │
│  │ (OSS)    │     │ (通义听悟等) │     │ (LLM API)   │  │
│  └──────────┘     └──────────────┘     └──────┬───────┘  │
│                                                │          │
│                              ┌─────────────────┼────────┐│
│                              │                 │        ││
│                         ┌────▼─────┐  ┌───────▼──┐  ┌──▼──┐
│                         │ 内容摘要  │  │ 关键词提取│  │违规  │
│                         │          │  │ 情感分析  │  │检测  │
│                         │          │  │ 行动项   │  │      │
│                         └────┬─────┘  └──────┬───┘  └──┬──┘
│                              │               │         │  │
│                              └───────┬───────┘         │  │
│                                      │                 │  │
│                              ┌───────▼──────────┐      │  │
│                              │  结果聚合 & 存储   │◀─────┘  │
│                              │  写入 DB + 通知    │         │
│                              └──────────────────┘         │
│                                                            │
│  处理流程（异步）：                                         │
│  1. 录音上传 → MQ 消息                                    │

│  5. 结果写入 DB → 如有违规，触发通知                       │
│                                                            │
│  违规检测策略：                                            │
│  ├── 第一层：关键词匹配（违规词库，高速）                  │
│  ├── 第二层：语义分析（LLM，识别隐含违规）                 │
│  └── 结合上下文判断，减少误报                              │
│                                                            │
│  性能优化：                                                │
│  ├── 异步队列处理，不阻塞业务                              │
│  ├── 优先级队列：违规检测高优先                            │
│  ├── 批量处理：攒批调用 LLM API                           │
│  └── 结果缓存：相似内容复用分析结果                        │
```

## 10. 开发阶段规划

### 10.1 里程碑

| 阶段 | 周期 | 核心交付 |
|---|---|---|
| **Phase 1: 基础框架** | 4 周 | 微服务骨架、多租户框架、鉴权集成、Gateway |
| **Phase 2: 核心 CRM** | 6 周 | 线索管理、客户管理、商机管理、跟进管理、数据权限 |
| **Phase 3: 分配与公海** | 3 周 | 线索分配（手动+自动）、公海池、转化流程 |
| **Phase 4: ERP 集成** | 4 周 | ERP 适配层、客户同步（双向）、审核流程 |
| **Phase 5: 外勤 APP** | 6 周 | APP 基础框架、签到打卡、拜访管理、任务管理 |
| **Phase 6: AI 能力** | 4 周 | 录音采集、语音转写、AI 分析、违规检测 |
| **Phase 7: PC 前端** | 6 周 | PC 端所有页面、微前端集成、报表 |
| **Phase 8: 活动与社交** | 4 周 | 活动管理、二维码、好友管理、企业微信集成 |
| **Phase 9: 扩展功能** | 4 周 | 行动轨迹、五度易链企业查询、黑名单、采购日期、销售员报表 |
| **Phase 10: 性能优化** | 4 周 | 缓存优化、分库分表、压测调优 |
| **Phase 11: 上线准备** | 3 周 | 安全审计、压力测试、灰度发布、文档 |

**总计：约 48 周（12 个月）**
